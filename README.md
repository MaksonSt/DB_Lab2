## Що зроблено

### 1. Основні види NoSQL баз

| Тип | Модель даних | Приклади | Коли доречний | Коли ні |
|---|---|---|---|---|
| Документні | JSON/BSON-документи з вкладеними об'єктами й масивами, гнучка схема | MongoDB, Couchbase | агрегат читається й пишеться цілком; структура різна в різних записах або часто змінюється (каталоги, профілі, протоколи, CMS) | багато зв'язків між сутностями, транзакції через кілька агрегатів, жорсткі обмеження цілісності |
| Key-value | ключ → значення (рядок, хеш, список, множина…), часто в пам'яті | Redis, DynamoDB, etcd | кеш, сесії, лічильники, черги, рейтинги, блокування з TTL, pub/sub — прості операції за ключем з мінімальною затримкою | запити за значенням, складні вибірки й звіти, дані більші за пам'ять |
| Колонкові (wide-column) | рядки з динамічними колонками, розподіл за ключем партиції; аналітичні колонкові СУБД зберігають дані по колонках | Cassandra, HBase, ClickHouse | великі потоки запису (телеметрія, логи, події), часові ряди, аналітика по мільйонах рядків, запити наперед відомі | ad-hoc запити, JOIN, часті точкові оновлення, малі обсяги |
| Графові | вузли й ребра з властивостями | Neo4j, ArangoDB | глибокі зв'язки: соціальні графи, рекомендації, маршрути, пошук шляхів і спільних зв'язків | масові агрегації по атрибутах, табличні звіти, прості CRUD |

### 2. Аналіз предметної області

**Чи варто виносити наявні дані ЛР 1 в іншу БД?** Ні — і ось чому:

- команди, спортсмени, склади, заявки, квитки, спонсори — це сутності з багатьма зв'язками (`teams` ↔
  `athletes` ↔ `events` ↔ `matches`), їх змінюють точково і по кілька в одній транзакції;
- бізнес-правила (вільні місця, дедлайн реєстрації, вид спорту команди, унікальність назви, спортсмен
  лише в одній команді) реалізовані обмеженнями, тригерами й процедурами — це сильна сторона РСУБД;
- квитки й спонсорські суми — гроші, тут потрібні ACID-транзакції;
- обсяги малі (сотні команд, тисячі спортсменів), структура стабільна.

Кандидати, які розглядались і були відкинуті: квитки в key-value (втрачаються транзакції й звіти),
спонсори/склади в графову БД (зв'язки неглибокі, JOIN на двох рівнях PostgreSQL робить швидко).

**Тому вимоги розширено** (`docs/requirements.md`, пп. 10–15): система веде **протоколи матчів**.
Протокол — природний кандидат на документну модель:

| Властивість даних | Наслідок |
|---|---|
| Структура залежить від виду спорту: у футболі тайми, голи з асистентом, картки, заміни; у баскетболі чверті, фоли з типом, таймаути без гравця, кидки із сиреною; різні набори показників гравця | у SQL — або таблиця з десятком nullable-колонок під кожен вид спорту, або EAV (`player_match_stats` + `stat_definitions`); документ просто містить потрібні поля |
| Новий вид спорту / новий показник | у документі — без міграції; у SQL — новий рядок у довіднику, а нова колонка події — `ALTER TABLE` |
| Протокол читають цілком (сторінка матчу) | один документ замість JOIN п'яти таблиць і ~180–220 рядків статистики |
| Протокол пишеться один раз і майже не змінюється | денормалізація (імена гравців, назви команд у документі) не створює проблем з оновленням |
| Протокол — самостійний агрегат | транзакції між кількома протоколами не потрібні; атомарності одного документа достатньо |
| Обсяг: ~200 рядків статистики на матч, сотні тисяч матчів | таблиця статистики в SQL росте до десятків мільйонів рядків |

Для **live-даних матчу** (табло, стрічка, лічильники, рейтинг) доречна key-value БД — п. 6.

### 3. Реалізація в MongoDB

Обрано **документну БД MongoDB**: протокол — це агрегат, який читається одним запитом без JOIN; гнучка
схема знімає проблему різних наборів полів для різних видів спорту; aggregation pipeline (`$unwind`,
`$group`) покриває турнірну аналітику; є вторинні й multikey-індекси по полях вкладених масивів.
Колонкова БД (Cassandra) тут гірша: потрібні запити наперед, немає гнучких агрегацій; графова — не та
форма даних; key-value — немає запитів за вмістом.

Документ (`app/src/models.ts`, `MatchReport`), скорочено:

```json
{
  "matchId": 2, "eventId": 8, "sportId": 1, "sport": "Футбол",
  "playedAt": "2025-06-14T18:00:00Z", "attendance": 23810,
  "teams":   [{ "teamId": 23, "name": "ФК Ген-19", "isHome": true, "score": 3 }, { "...": "..." }],
  "periods": [{ "number": 1, "home": 1, "away": 0 }, { "number": 2, "home": 2, "away": 3 }],
  "timeline": [
    { "period": 1, "minute": 7,  "type": "yellow_card",  "teamId": 23, "athleteId": 334 },
    { "period": 1, "minute": 31, "type": "goal", "teamId": 23, "athleteId": 336, "relatedAthleteId": 341, "note": "header" },
    { "period": 2, "minute": 62, "type": "substitution", "teamId": 24, "athleteId": 360, "relatedAthleteId": 352 }
  ],
  "playerStats": [
    { "athleteId": 331, "name": "Денис Руденко", "teamId": 23,
      "stats": { "minutes": 90, "goals": 0, "assists": 0, "shots": 2, "passes": 63, "fouls": 2, "saves": 0 } }
  ]
}
```

У баскетбольному протоколі 4 періоди, у хронології `foul` з `note`, `timeout` без `athleteId`,
`buzzer_beater` з `points`, а `stats` містить `points`, `rebounds`, `steals`, `blocks`, `threes`…

- підключення та індекси: `app/src/mongo/mongo.ts`;
- репозиторій: `app/src/mongo/MongoMatchReportRepository.ts` (`insertOne/insertMany`, `findOne`,
  `aggregate`, `updateOne` з `$push` + `$inc` і `arrayFilters`, `$set`, `deleteMany`);
- запис з `writeConcern { w: 1, j: true }` — підтвердження після запису в журнал, як `COMMIT` у PostgreSQL.

### 4. Те саме в PostgreSQL

Документ розкладено на 5 таблиць (`sql/08_match_reports.sql`), з посиланнями на таблиці ЛР 1:

| Частина документа | Таблиця | Примітка |
|---|---|---|
| `matchId`, `attendance` | `match_reports` | 1 рядок на матч, `UNIQUE (match_id)` |
| `eventId`, `sport`, `playedAt`, `teams[]` (рахунок) | `matches`, `events`, `sports`, `match_participants`, `teams` | уже є в ЛР 1 |
| `periods[]` | `match_report_periods` | PK `(report_id, period_no)` |
| `timeline[]` | `match_report_events` | `seq` зберігає порядок; поля, специфічні для спорту (`related_athlete_id`, `points`, `note`) — nullable |
| `playerStats[].stats{}` | `player_match_stats` + `stat_definitions` | EAV: рядок на кожен показник гравця; довідник показників по видах спорту |
| `playerStats[].name` | `athletes` | у SQL не дублюється |

Доступ — як у ЛР 1: зміни лише через процедури, читання через view та функції (`sql/09`, `sql/10`):

- `sp_match_reports_import(jsonb)` — вставка одного або пакета протоколів одним set-based запитом;
- `sp_match_report_add_event`, `sp_match_report_set_attendance`, `sp_match_reports_delete`;
- `v_match_reports` — збирає з 5+ таблиць документ тієї ж форми, що в MongoDB;
- `fn_event_top_players`, `fn_athlete_stat_averages`, `fn_event_matches_with`, `v_event_card_counts`.

Репозиторій `MatchReportRepository` реалізує той самий інтерфейс `MatchReportStore`, що й Mongo-репозиторій,
і доданий в `UnitOfWork`. `npm run demo` показує:

1. футбольний і баскетбольний протоколи (різна структура);
2. що протоколи, зібрані з PostgreSQL, **ідентичні** документам MongoDB (40 з 40);
3. однакові результати агрегацій в обох БД;
4. оновлення (гол на 90+3) в обох БД;
5. ROLLBACK у `UnitOfWork`;
6. гнучкість проти цілісності: MongoDB приймає новий показник `dunks` без змін схеми,
   PostgreSQL відхиляє протокол, доки показник не додано в `stat_definitions`.

### 5. Порівняння швидкодії

**Методика** (`app/src/bench`):

- однакові дані: детермінований генератор (`app/src/generator`) створює в PostgreSQL 20 подій, 48 команд,
  720 спортсменів і матчі, а потім однакові протоколи для обох БД (~180 показників і 15–60 подій на протокол);
- обсяги: 1 000, 10 000, 50 000 протоколів у базі; на кожному обсязі — однаковий набір сценаріїв;
- однакові індекси:

  | Призначення | PostgreSQL | MongoDB |
  |---|---|---|
  | протокол за матчем | `ux_match_reports_match_id` | `{ matchId: 1 }` unique |
  | фільтр за подією | `ix_matches_event_id` | `{ eventId: 1 }` |
  | статистика спортсмена | `ix_player_match_stats_athlete_id` | `{ "playerStats.athleteId": 1 }` |
  | тип події в хронології | `ix_match_report_events_type` | `{ "timeline.type": 1 }` |

- 1 прогрів + 7 вимірюваних прогонів, у таблиці — **медіана**; порядок БД чергується між прогонами;
  вставлені в сценаріях вставки протоколи видаляються після кожного прогону (поза заміром);
- однакова довговічність: PostgreSQL `synchronous_commit = on`, MongoDB `j: true`;
- після кожного завантаження — `VACUUM ANALYZE`; після сценаріїв — перевірка, що агрегації в обох БД збігаються.

| Сценарій | Що перевіряє |
|---|---|
| Вставка по одному (100) | типовий запис протоколу після матчу |
| Пакетна вставка (1 000) | імпорт сезону / міграція |
| Читання цілого протоколу (200) | сторінка матчу — головний сценарій читання |
| Матчі з певною подією (20 подій) | фільтр за полем вкладеного масиву |
| Топ-10 гравців події (20) | агрегація по підмножині (індекс за подією) |
| Середні показники спортсмена (50) | агрегація «впоперек» документів (індекс по вкладеному полю) |
| Картки по всіх подіях (3) | агрегація з проходом по всіх даних |
| Додати подію + показник (200) | зміна вкладених масивів |
| Оновити відвідуваність (200) | зміна поля заголовка |

PG / Mongo для 1k · 10k · 50k (більше 1 — швидша MongoDB, менше 1 — швидший PostgreSQL):

| Сценарій | Операцій у серії | 1 000 | 10 000 | 50 000 | PG / Mongo |

| Пакетна вставка протоколів | 1000 | 10.0 / 0.37 | 9.7 / 0.38 | 9.3 / 0.43 | 27.07 · 25.54 · 21.74 |
| Читання цілого протоколу за matchId | 200 | 3.7 / 1.8 | 3.7 / 1.6 | 4.3 / 1.7 | 2.12 · 2.36 · 2.60 |
| Матчі події з певним типом події в хронології | 20 | 3.4 / 2.2 | 11 / 7.9 | 54 / 26 | 1.56 · 1.43 · 2.09 |

Обсяг на диску при 50 000 протоколів (дані + індекси, після `fsync`): PostgreSQL — **1198 МБ**
(8,9 млн рядків `player_match_stats`, 1,8 млн рядків `match_report_events`), MongoDB — **121 МБ**
(376 МБ документів до стиснення, середній документ 7,9 КБ).

**Висновки**

1. **Запис — перевага MongoDB: у 2,7–2,9 раза по одному протоколу, у 22–27 разів пакетом.** Документ записується одним об'єктом, а в PostgreSQL той самий
   протокол — це ~180 рядків статистики й ~35 подій у 4 таблицях. `EXPLAIN ANALYZE` імпорту 300 протоколів
   показав, що ~80% часу займають перевірки зовнішніх ключів (по 4 FK на кожен рядок статистики),
   сам `INSERT` — лише ~0,4 с з 2,6 с. Це ціна цілісності: MongoDB таких перевірок не робить.
2. **Читання цілого протоколу — MongoDB у 2,1–2,6 раза швидша** і не сповільнюється з ростом даних:
   документ читається за індексом `matchId` одним зверненням, а PostgreSQL збирає його з 5+ таблиць
   (`jsonb_agg`, `jsonb_object_agg`, JOIN з `athletes`). Для головного сценарію читання документна модель виграє.
3. **Агрегації «впоперек» документів — перевага PostgreSQL у 2–4 рази** (середні показники спортсмена,
   картки по всіх подіях). PostgreSQL читає лише потрібні вузькі рядки (`player_match_stats` за індексом
   `athlete_id`, `match_report_events` за типом), а MongoDB мусить підняти й розгорнути (`$unwind`) цілі
   документи по 8 КБ, щоб дістати кілька чисел. Відрив PostgreSQL зростає з обсягом.
4. **Агрегації в межах події** (топ гравців, фільтр за вкладеним полем) — MongoDB швидша в 1,4–2 рази:
   фільтр за `eventId` одразу дає потрібні документи, PostgreSQL додатково з'єднує `matches` і `match_reports`.
   Але обидві БД тут ростуть лінійно з кількістю матчів у події.
5. **Оновлення.** Зміна поля заголовка — паритет (у MongoDB трохи швидше). Додавання події з `$push` +
   `$inc` за `arrayFilters` у MongoDB повільніше в ~1,6 раза: переписується весь документ 8 КБ, тоді як
   PostgreSQL вставляє один рядок і оновлює один рядок статистики.
6. **Обсяг:** EAV-нормалізація роздуває дані — PostgreSQL займає в ~10 разів більше місця (заголовки рядків,
   дублювання `report_id`/`athlete_id`, індекси), MongoDB ще й стискає документи (snappy).

**Підсумок.** Для протоколів матчів (пишуться раз, читаються цілком, структура залежить від виду спорту)
документна БД доречніша: швидший запис і читання, гнучка схема, у 10 разів менший обсяг. PostgreSQL
залишається кращим для аналітики по всьому масиву і для даних з ЛР 1, де потрібні зв'язки й транзакції.
Практичне рішення — гібрид: протоколи в MongoDB, довідники й облік у PostgreSQL, live-дані в Redis.

### 6. Redis (key-value)

`npm run redis-demo` (`app/src/redis-demo.ts`) — live-шар матчу. Усі ключі мають префікс `lab2:`
і видаляються наприкінці.

| Структура | Команди | Застосування |
|---|---|---|
| String + TTL | `SET … EX`, `GET`, `TTL` | кеш картки матчу на 30 с |
| String-лічильник | `INCR`, `INCRBY`, `DECR` | продані квитки (атомарно, без гонок) |
| Hash | `HSET`, `HGET`, `HGETALL`, `HINCRBY` | live-табло: рахунок, хвилина, статус |
| List | `LPUSH`, `LTRIM`, `LRANGE`, `LLEN` | стрічка останніх 5 подій |
| Set | `SADD`, `SCARD`, `SISMEMBER`, `SINTER` | підписники матчів, спільні підписники |
| Sorted set | `ZADD`, `ZINCRBY`, `ZRANGE … REV WITHSCORES`, `ZREVRANK`, `ZSCORE` | рейтинг бомбардирів |
| String + `NX EX` | `SET key val NX EX 600` | бронювання місця на 10 хв: друга спроба повертає `null` |
| Транзакція | `MULTI` / `EXEC` | гол атомарно змінює табло, стрічку й рейтинг |
| Pub/Sub | `SUBSCRIBE`, `PUBLISH` | сповіщення про гол підписникам |
| Ітерація | `SCAN MATCH lab2:*`, `DEL` | пошук і очищення ключів без блокування сервера |

Redis не замінює ні PostgreSQL, ні MongoDB: дані live-шару тимчасові (TTL), а після матчу фінальний
стан записується протоколом у документну БД.
